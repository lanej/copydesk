# Editor interoperability protocol v1

The [Protobuf service](../proto/editorinterop/v1/editor_interop.proto) defines the wire contract. The [host interfaces](../src/host.ts) define the in-process provider, launcher and workspace. [Authority and recovery](architecture.md) describes guarantees that message validation alone cannot establish.

## Ownership and public exports

The independent package exports `createWorkspace`, the provider/launcher interfaces and generated v1 schemas/types. `createWorkspace(options)` creates the private directory, socket, manifest and projection directory, subscribes to `provider.onChanged`, performs the initial refresh, and opens the companion automatically once a document exists. Studio supplies the opaque `CallContext`, provider, launcher, packaged Neovim runtime directory, working directory and readable title. The core generates credentials and launch IDs; Studio does not implement the wire server.

The returned `EditorWorkspace` exposes `manifestPath`, `refresh()`, `open()` and `dispose()`. `refresh()` coalesces concurrent requests and serializes projection replacement against accepted saves. `open()` is explicit reopen: reconcile the existing attachment before clearing manual-close suppression and issuing a new launch. It must not create a duplicate pane when attachment state is uncertain. A verified live pane is reused. `dispose()` stops endpoint/subscriptions and closes transient snapshot readers; it preserves editor text, recovery files and authoritative receipts. Replacing an activation requires disposal and a fresh generation supplied by Studio; it never reuses the old activation credential.

`HostProvider.openSnapshot` supplies a consistent, incremental view, `save` supplies an atomically witnessed result, `submitFeedback` persists the exact request before admission, and `onChanged` invalidates projections. The provider owns all workflow and conversation decisions. The core adds each wire `DocumentView.projectionPath`; the provider returns path-free `DocumentSnapshot` values. Paths are absolute, core-issued and beneath `ConnectionManifest.projectionDirectory`, with no symlink escape or duplicate mapping. The client retains the exact document-to-path mapping and never derives authority from a pathname. The Lua write handler sends captured buffer text through `Save`; writing an authoritative projection file is not an alternative commit path.

`EditorLauncher.ensure` launches or reuses an attachment for the issued `LaunchRequest`; `inspect` resolves its opaque attachment ID; `verifyRegistration` checks the actual process/start identity and RPC endpoint against that launch; `dispose` releases owned observers. Studio's adapter owns Zellij commands and pane verification. A fake launcher can verify a directly spawned headless Neovim process without Zellij.

## Exact HTTP envelope and registration

Every call is an HTTP/1.1 POST over the manifest's private Unix socket to `/editorinterop.v1.EditorInteropService/<Method>`, where `<Method>` is exactly `Register`, `Sync`, `Save`, `Feedback` or `Result`. The JSON body is the corresponding Protobuf request. There is no extra handwritten request envelope, newline frame, HTTP GET RPC or required streaming support. A successful response is HTTP 200 with the corresponding Protobuf response body. [Connect protocol](https://connectrpc.com/docs/protocol/).

The Lua edge sends `Host: localhost`, `Content-Type: application/json`, `Connect-Protocol-Version: 1`, `Authorization: Bearer <manifest.bearerToken>`, `Content-Length` measured in encoded bytes, and `Connection: close`. `Connection: close` is a narrow client implementation choice, not identity. It reads the complete HTTP response, supports valid Content-Length and chunked transfer coding, and enforces the 65,536-byte response-body cap during decoding. v1 sends no HTTP content compression. The TypeScript adapter uses generated Connect clients/server bindings. Lua implements this small HTTP/Connect-JSON edge and validates the schema-derived response shapes; it does not claim an official generated Lua Connect or Protovalidate runtime.

Each bearer credential belongs to one issued launch and exactly one verified `EditorRegistration`. Before registration it authorizes only `Register`; afterward it binds every unary request to that registration, the fixed session and generation. A new HTTP connection carries the same bearer binding. `Register` verifies the manifest context, application version, launch ID, editor instance ID, PID and RPC address through the launcher before admitting other methods. An identical repeat is idempotent after verification. A differing registration cannot replace a live one. Explicit reopening reconciles the former process, invalidates its credential/cursors and issues a fresh launch ID/token. The private directory is mode 0700 and manifest/socket mode 0600; tokens are never logged or embedded in projection text.

Authentication and generation/version/registration checks precede provider effects. The provider checks current owner and activation again immediately before a write or conversation admission, including after awaited work. Old credentials, cursors or editable projection contents cannot establish a new binding.

## Application version and JSON semantics

Connect's `Connect-Protocol-Version: 1` is separate from `ProtocolVersion {major: 1, minor: 0}`. The current application implements only v1.0 and all of its features are mandatory. A registering client advertises its highest implemented minor and must also implement minor zero; the server selects the highest mutually supported minor, currently zero. Each peer encodes only that selected shape. Major mismatch or no compatible version fails before effects. A later minor must preserve the baseline, have explicit compatibility fixtures and provide selected-minor encoders. It cannot silently add a required field or weaken save/feedback guarantees.

JSON uses the standard ProtoJSON field names and defaults: omitted scalar defaults mean zero/false/empty; the `SyncComplete {}` value is a valid empty snapshot; `optional` fields preserve presence; `oneof` permits exactly one selected member. Encoders use lowerCamelCase field names, symbolic enum names, padded standard base64 bytes and decimal-string uint64 values. Decoders follow ProtoJSON acceptance rules but reject unknown fields, unknown enum values, missing required messages, invalid oneofs and failed Protovalidate constraints. Lua must preserve uint64 strings and use exact decimal arithmetic/comparison, never lossy floating-point conversion. [ProtoJSON mapping](https://protobuf.dev/programming-guides/json/).

## RPC results and completeness

| Method | Request | Response and effect |
|---|---|---|
| `Register` | `RegisterRequest` | `RegisterResponse` selects version and confirms fixed limits after process verification. No document/chat effect. |
| `Sync` | `SyncRequest`; empty cursor starts | `SyncResponse`: header, bounded item chunks, then complete counts. A continuation is read-only. |
| `Save` | `SaveRequest` with stable operation ID | `SaveResponse` contains the first chunk of a typed `SaveResult`. Exact repeats resolve the original atomic witness; different payload reuse is rejected. |
| `Feedback` | `FeedbackRequest` with stable request ID | `FeedbackResponse` contains the first chunk of a persisted `FeedbackRecord`. Exact repeats read its receipt and never dispatch again. |
| `Result` | `ResultRequest` with continuation cursor | `ResultResponse` supplies the next save/feedback result chunk without repeating an effect. |

A `SyncResponse` header establishes the authorized session and optional active owner. Its `snapshotId` remains constant and `sequence` starts at decimal `"1"`, increasing by one per page. Each item is one `ValueChunk`; chunks of different values do not interleave. `VALUE_KIND_DOCUMENT` carries a completed `DocumentView`, `VALUE_KIND_FEEDBACK` a `FeedbackRecord`, and `VALUE_KIND_SAVE_RESULT` a `SaveResult`. Sync permits only document/feedback kinds; operation continuations permit only feedback/save-result kinds. Completed values are compact UTF-8 ProtoJSON, validated against these generated types after reconstruction. SHA-256 binds the exact serialized bytes; no cross-language JSON canonicalization is needed.

A value starts at offset zero. Its transfer ID, kind, totalBytes and digest are constant; each offset equals the prior offset plus decoded data length. `valueComplete` is true exactly at totalBytes. A raw fragment may split a UTF-8 character or JSON escape, so decode base64 bytes first, stage/concatenate them, verify length and digest, then perform strict UTF-8, JSON and typed validation. Reject duplicate document identities, receipt IDs, projection paths, foreign sessions and document owners different from the header. Only a final `SyncComplete` with exact verified item counts authorizes membership changes. A complete snapshot with no active owner has no documents; historical owner-bound receipts may still be present.

The client tracks a local synchronization epoch as well as snapshot ID. Starting another sync, saving or commenting invalidates a captured older epoch. An older asynchronous completion cannot replace newer buffers. Page sequence numbers order pages within one snapshot, not revisions across snapshots. A clean buffer refresh is one undoable text replacement with visible changes. A dirty buffer retains its text and stages the incoming revision for explicit comparison/reconciliation; neither a partial sync nor a newer host revision silently overwrites it.

## Bounds, cursors and recovery

Encoded unary requests are limited to 33,554,432 bytes, response pages to 65,536 bytes and raw `ValueChunk.data` to 32,768 bytes. Save input is limited to 2,000,000 Unicode scalar values; selected feedback text to 100,000 and the message to 20,000. These input limits are separate from encoded-byte checks. Even a compact request using surrogate escapes for every allowed supplementary scalar fits below the 32 MiB cap. Invalid or excessive input fails before provider effects and retains the complete editor candidate.

Read values have no total size or history ceiling. A single valid host document larger than the request cap remains readable through multiple chunks; it is never truncated to become a valid save candidate. The host reader and core spool one logical item at a time instead of capturing a workspace aggregate. Memory is bounded by the host's current logical record plus fixed serialization/transport buffers; the editor may materialize a complete current record but stages the history on private disk. Disk exhaustion or inability to obtain a consistent snapshot is an explicit failed read, preserving previous editor state.

A cursor binds to the registration, generation, session, transfer and next position. Each registration permits one active sync and four unfinished operation-result transfers. Starting a fresh sync supersedes only the old read view. Single-page replies have no Result cursor and release the transient slot immediately; exact repeats read the provider's durable witness/receipt. Completed multi-page results retain final replay pages in a separate cache of at most 64 entries. A new state-changing call reserves unfinished-transfer and completed-replay capacity before invoking the provider; exhaustion rejects before effects. An exact duplicate of an unfinished operation reuses its transfer. Authenticated offset cursors reconstruct evicted earlier pages from the retained immutable spool without repeating the provider call. The core caches only current and preceding response pages. After completion, a fresh exact command reads the provider's durable witness or receipt into a new transfer while the original final cursor remains replayable. Repeating a retained final cursor returns identical bytes. Cursor replay does not renew the lease. A transfer expires after 60 seconds without forward progress and has no absolute duration limit while progressing; a completed transfer retains its final cursor page for 60 seconds. On completion/expiry/cancellation, close readers and release private transient spool/cache data, preserving durable receipts and recovery text.

Empty continuation means a complete operation result, or the final complete sync page. A lost final response is retried with the same final request cursor. Expiry returns `not_found`; incomplete staged pages never detach documents or erase outcomes. Starting a new sync reads fresh state and never resubmits feedback. A lost state-changing response leaves its operation uncertain. Explicit repeated Save with the exact command may read its atomic witness; uncertain feedback is inspected through Sync and is never automatically replayed. Generation changes retain answered and confirmed-failed outcomes while unfinished queued/dispatching/awaiting/parked records become uncertain with their original evidence.

## Errors

Connect errors use `Content-Type: application/json` with its standard `{code, message, details?}` body. Details follow Connect's format rather than a custom envelope. These exact HTTP mappings follow the [Connect error table](https://connectrpc.com/docs/protocol/#error-codes).

| Condition | Connect code | HTTP | Client handling |
|---|---|---|---|
| Invalid token | `unauthenticated` | 401 | Keep text and pending evidence; require explicit reconnection. |
| Wrong generation, unregistered client, incompatible version or stale launch | `failed_precondition` | 400 | No effects; retain buffers and reconcile connection. |
| Malformed/unknown-field/invalid constrained message | `invalid_argument` | 400 | No effects; retain complete candidate and show reason. |
| Request ID reused with different feedback content | `already_exists` | 409 | No additional dispatch; retain original receipt. |
| Expired/unknown cursor | `not_found` | 404 | Discard only incomplete staged pages; read fresh state. |
| Encoded message too large or result slots full | `resource_exhausted` | 429 | No new provider effect; keep candidate. |
| Unexpected provider/transport failure | `internal` / connection loss | 500 / no response | Do not infer success or rollback; keep pending identity and reconcile evidence. |

Expected save conflicts, protected changes, invalid Markdown and reused operation IDs are typed `RejectedSave` results, not transport success claims. An authoritative witness is required for `AcceptedSave`. A provider reports pre-effect feedback failures through the exported `ProviderError` codes; unexpected errors never authorize automatic retry. Protobuf validation cannot establish transaction atomicity, actual conversation admission, process identity or response attribution; implementation checks must prove those facts.
